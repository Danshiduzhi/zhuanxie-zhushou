## 二、Additional Information（约 200 词，可放项目描述）

```
Transcription Assistant — Independent Software Project (Aug–Oct 2026)

I record most of my lectures and interviews, and every transcription option I tried had a
problem: online services charge by the minute and upload private conversations to a third
party; built-in features lock exports into one ecosystem; open-source Whisper requires
command-line fluency that none of my classmates have.

So I built the alternative. A Windows application that bundles Whisper large-v3 (2.9 GB)
and runs entirely offline. Drop in a video, get back a transcript, an AI-generated summary,
the extracted audio, and subtitles — four files, one folder, ready to hand to a client.

Two engineering problems shaped the project. First, long transcripts exceeded the language
model's output limit, so the correction pass silently dropped the second half of a
47-minute interview. I solved it with chunked correction and timestamp-anchored merging, so
no line can be lost. Second, my first release put user data inside the program folder,
inflating it to 9 GB and crashing on read-only install locations; separating application
and data directories, with a migration path for existing users, fixed it.

The project taught me that shipping costs more than coding: packaging, logging, error
recovery, and data migration took two-thirds of the work. I also removed a working
speaker-identification feature because it added 3 GB of dependencies for unreliable output —
a decision to prioritize the product over the feature list.
```

## 三、文书可用素材（三个真实故事角度）

### 角度 1：从"能用"到"能交付"
> 功能写完只占三分之一。真正的坎是打包、日志、崩溃恢复、老数据迁移。
> 我第一次发布时，用户把程序装到 Program Files 直接闪退——因为我把数据写在了程序目录里。

**可提炼：** 对"完成"的标准一旦提高，就会看见看不见的工作。

### 角度 2：主动砍功能的克制
> 说话人区分（谁在说话）我做出了能跑通的版本。但要额外打包 3 GB 的 PyTorch 依赖，
> 真实录音里准确率还不稳定。我把它删了，安装包从 7 GB 降到 3.3 GB。

**可提炼：** 判断什么该做、什么该删，比能不能做更重要。

### 角度 3：一次"数据消失"debug
> 47 分钟的访谈稿送去 AI 校对，回来的字数少了一半。查下去才发现是模型输出有上限，
> 而且它还会自作主张合并句子。我用时间戳做锚点逐行对齐，缺的行从原文补回。

**可提炼：** 面对黑箱，先建立可验证的对齐机制，而不是相信它的输出。

## 四、中文简历版（一页简历用）

**转写助手｜独立开发｜2026.08 – 2026.10**

一款本地离线运行的音视频转写桌面软件，把视频/录音自动转成可交付的 Word 文档。

- 独立完成产品定义、技术选型、全部实现、打包分发与软件著作权申请
- 技术栈：Python 3.12、Flask、faster-whisper（Whisper large-v3）、python-docx、ffmpeg、PyInstaller、Inno Setup、原生 JS
- 代码量 4,261 行，19 个文件；Windows 一键安装包 3.3 GB（含离线模型）
- 解决三个关键工程问题：
  - 大模型输出截断导致长文稿丢行 → 分块校对 + 时间戳锚点对齐合并，一行不丢
  - CUDA 动态库无法随包分发 → 导入期注入 DLL 搜索路径，解决打包后启动失败
  - 用户数据混入程序目录 → 程序/数据目录分离 + 兼容迁移，解决只读目录崩溃
- 真实数据验证：47 分钟访谈视频端到端跑通，每视频输出 4 份产物
- 软件著作权已提交中国版权保护中心（受理号 2026R11L3085396）
- 另实现手机端 PWA，iOS/Android 通用，直连用户自配置的识别 API

## 五、面试可能被问到的问题

| 问题 | 回答要点 |
|---|---|
| 为什么不用现成的在线服务？ | 成本、隐私、导出格式三个角度；再加上"我同学没有人会用命令行"这个真实约束 |
| 最大的技术难点？ | 不是识别本身，是让大模型的输出"可对齐、可回退"——时间戳锚点合并 |
| 为什么删掉说话人区分？ | 3 GB 依赖换不稳定的准确率，安装体验更重要 |
| 项目里最后悔的决定？ | 一开始没做数据目录分离，导致第一版要重做打包方案 |
| 如果重做会怎么改？ | 先定数据和生命周期边界（哪些是用户数据、哪些是程序资源），再写功能 |
