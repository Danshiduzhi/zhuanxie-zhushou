## 二、Additional Information（约 200 词，可放项目描述）

```
Transcription Assistant — Independent Software Project (Aug–Oct 2026)

I am self-taught in Python and C — never took a programming course. I learned both by
reading documentation until the pieces fit, which is how this project got built.

It started with people around me. Classmates handed me lecture recordings asking whether
they could become text; a friend was transcribing interviews until 3 a.m. Every existing
option failed them: online services charge by the minute and upload private conversations to
a third party; built-in features lock exports into one ecosystem; open-source Whisper
requires command-line fluency that none of them have.

So I built the alternative. A Windows application that bundles Whisper large-v3 (2.9 GB)
and runs entirely offline. Drop in a video, get back a transcript, an AI-generated summary,
the extracted audio, and subtitles — four files, one folder, ready to hand to someone.

Two engineering problems shaped the project. First, long transcripts exceeded the language
model's output limit, so the correction pass silently dropped the second half of a
47-minute interview. I solved it with chunked correction and timestamp-anchored merging, so
no line can be lost. Second, my first release put user data inside the program folder,
inflating it to 9 GB and crashing on read-only install locations; separating application
and data directories, with a migration path, fixed it.

Shipping cost more than coding: packaging, logging, error recovery, and data migration took
two-thirds of the work. I also removed a working speaker-identification feature because it
added 3 GB of dependencies for unreliable output — prioritizing the product over the
feature list.
```

## 三、文书可用素材（四个真实故事角度）

### 角度 1：从"能用"到"能交付"
> 功能写完只占三分之一。真正的坎是打包、日志、崩溃恢复、老数据迁移。
> 我第一次发布时，用户把程序装到 Program Files 直接闪退——因为我把数据写在了程序目录里。

**可提炼：** 对"完成"的标准一旦提高，就会看见看不见的工作。

### 角度 2：主动砍功能的克制
> 说话人区分（谁在说话）我做出了能跑通的版本。但要额外打包 3 GB 的 PyTorch 依赖，
> 真实录音里准确率还不稳定。我把它删了，安装包从 7 GB 降到 3.3 GB。

**可提炼：** 判断什么该做、什么该删，比能不能做更重要。

### 角度 3：一次"数据消失"debug
> 47 分钟的访谈稿送去 AI 校对，回来的字数少了一半。查下去才发现是模型输出有上限，
> 而且它还会自作主张合并句子。我用时间戳做锚点逐行对齐，缺的行从原文补回。

**可提炼：** 面对黑箱，先建立可验证的对齐机制，而不是相信它的输出。

### 角度 4：没有老师的那部分
> Python 和 C 都是自学。做这个项目时遇到三个没人能问的问题：
> PyInstaller 打包后找不到 CUDA 动态库、老数据字段类型不一致导致接口崩、长文本超出模型上下文。
> 每一个都是靠读官方文档、看报错栈、改一行跑一次试出来的。
> 后来同学把网课录屏丢给我，说"这个能转成文字吗"——那一刻我知道这东西不是练手项目。

**可提炼：** 自学的本质是把"看不懂"拆成能验证的小问题，然后一个一个试。

## 五、面试可能被问到的问题

| 问题 | 回答要点 |
|---|---|
| 为什么不用现成的在线服务？ | 成本、隐私、导出格式三个角度；再加上"我同学没有人会用命令行"这个真实约束 |
| 最大的技术难点？ | 不是识别本身，是让大模型的输出"可对齐、可回退"——时间戳锚点合并 |
| 为什么删掉说话人区分？ | 3 GB 依赖换不稳定的准确率，安装体验更重要 |
| 项目里最后悔的决定？ | 一开始没做数据目录分离，导致第一版要重做打包方案 |
| 如果重做会怎么改？ | 先定数据和生命周期边界（哪些是用户数据、哪些是程序资源），再写功能 |
| 你自学到什么程度？ | 不说"会 Python"，说"能独立交付一个 4,261 行、带安装包的 Windows 软件"；C 用在 3D 打印机固件和硬件调试上 |
| 有没有人指导？ | 没有。遇到问题靠官方文档、报错栈和最小复现实验，一个变量一个变量试 |
